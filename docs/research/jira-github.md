# Jira Cloud and GitHub credential onboarding

Checked 2026-09-11 against first-party documentation and local DeepSeek Harness HEAD `c291e7961a515f6d7af9304e7fd1d257929aef26`. This note records provider and platform facts; product behavior remains in the specifications.

## Recommendation for the first single-VPS deployment

Do not make `.env` editing the normal path. Add one Autopilot Settings page with Jira and GitHub connection cards. Each card collects non-secret routing fields, accepts a secret in a masked one-time input, writes it through `ctx.remote.credentials.set`, then runs a Host-side access check and shows only configured/account/resource facts. DSH's credential Remote deliberately carries secret values only toward the Host and exposes only configured/source/writable metadata on reads; the local provider persists the result under the Harness home. The Settings shell already exposes a `settings.section` extension point for an external browser plugin. [credential Remote](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/api/settings-controller/src/credentials.ts#L60-L117), [local credential store](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/credentials/credentials-local/README.md#storing-and-removing-keys), [Settings slots](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/client/ui-settings/src/client/contract/slots.ts#L43-L74).

For the owner-operated v1 already holding credentials, use:

- **Jira:** site URL, bot email, project key, and a scoped API token. Provide an **Open Atlassian token page** link, **Save and verify**, **Replace**, and **Disconnect**. Atlassian tokens now support selected scopes and one-to-365-day expiry; scoped Jira tokens must call `https://api.atlassian.com/ex/jira/{cloudId}` rather than the site URL, so verification must resolve/store the selected site's cloud ID. [Atlassian token management](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/).
- **GitHub:** owner, repository, base branch, and a fine-grained PAT limited to that repository. Link to GitHub's prefillable fine-grained-token creation page with the owner and permissions filled where possible; the operator still selects the exact repository and pastes the resulting token once. GitHub documents repository selection, permission selection, organization approval, and URL-prefilled token forms. [fine-grained PATs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token), [prefilled token form](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#pre-filling-fine-grained-personal-access-token-details-using-url-parameters).

This token path has no callback or app registration, but it is not one-click: both providers require the human to create and copy a token. It is suitable only for this private, owner-operated deployment. Atlassian now states that cloud apps collecting customer API tokens, or telling customers to create individual 3LO apps, do not comply with its cloud-app requirements; a distributable product should provide one shared 3LO integration instead. [Jira basic-auth guidance](https://developer.atlassian.com/cloud/jira/platform/basic-auth-for-rest-apis/).

Use an SSH tunnel and the loopback DSH page for v1 administration. At this HEAD, the DSH Settings client intentionally disables Host persistence on non-loopback pages, and the shipped browser cookie is `SameSite=Strict`, not `Secure`; binding the built-in HTTP server directly to a public interface is unsupported. [Settings limitation](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/client/ui-settings/README.md#known-limitations-and-deferred-work), [browser authentication and request trust](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/client/connection/README.md#browser-authentication-and-request-trust).

## Least privilege

### Authenticated Jira webhook facts

Jira Cloud secure admin webhooks accept a secret and sign each request body with HMAC-SHA256 in `X-Hub-Signature`. Jira also sends `X-Atlassian-Webhook-Identifier`, which is unique within a tenant and remains the same across retries. Autopilot can therefore verify the exact request bytes before parsing them and hash the Cloud ID together with that identifier into a bounded, tenant-qualified durable delivery identity. The secret remains a DSH Credential reference and must never enter Settings or diagnostics. [Jira Software webhooks](https://developer.atlassian.com/cloud/jira/software/webhooks/), [Jira platform webhooks](https://developer.atlassian.com/cloud/jira/platform/webhooks/).

### Jira Cloud

For Autopilot's required project/issue search, issue and comment reads, changelog attribution, label edits, report comments, and configured status transitions, use the classic scopes `read:jira-work` and `write:jira-work`. Atlassian recommends classic scopes when available; these two cover issue/project reads and issue/comment writes. Add `offline_access` only for 3LO so the Host receives rotating refresh tokens. Do not request `read:jira-user`, `manage:jira-project`, `manage:jira-configuration`, or `manage:jira-webhook`; add `manage:jira-webhook` only if a later provider itself creates dynamic Jira webhooks. [Jira scope definitions](https://developer.atlassian.com/cloud/jira/platform/scopes-for-oauth-2-3LO-and-forge-apps/#classic-scopes), [3LO refresh tokens](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#how-do-i-get-a-new-access-token-if-my-access-token-expires-or-is-revoked), [issue search scope](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/#api-rest-api-3-search-jql-get), [comment-write scope](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-comments/#api-rest-api-3-issue-issueidorkey-comment-post).

Scopes are only a maximum. The bot account itself still needs **Browse Projects**, visibility through any issue security scheme, **Add Comments**, **Edit Issues** (labels), and **Transition Issues** for the one configured project and workflow; it needs no Jira administrator role. Jira explicitly states that user permissions continue to constrain scoped access. [scope and Jira-permission interaction](https://developer.atlassian.com/cloud/jira/platform/scopes-for-oauth-2-3LO-and-forge-apps/), [Jira REST authorization](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/#authentication-and-authorization).

### GitHub

Limit a fine-grained PAT or GitHub App installation to the one configured repository. Grant repository permissions **Metadata: read** (automatic), **Contents: read and write** for clone/fetch/push and branch refs, and **Pull requests: read and write** for reconciliation and PR creation. Do not grant Issues, Actions, Checks, Administration, Webhooks, organization, or account permissions for the specified v1. Add **Workflows: read and write** only if Autopilot is explicitly allowed to create or modify files under `.github/workflows`; otherwise reject such publication. [Git access permission](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app#choosing-permissions-for-git-access), [create PR permission](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request), [list PR permission](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests), [repository metadata permission](https://docs.github.com/en/rest/repos/repos#get-a-repository), [workflow-file exception](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents).

## What can be redirected from Settings

| Method | Callback/app prerequisites | Single-VPS result |
| --- | --- | --- |
| Jira API token | None; human creates and pastes the token | A button can open token management, but cannot complete authorization automatically. Owner-operated v1 only. |
| Jira OAuth 2.0 3LO | Atlassian developer-console registration, exact callback URL, client ID and client secret; code grant only. `offline_access` is required for refresh. | Deployment inference: the same VPS can own the configured callback route, so one fixed deployment needs no second callback service. It is not zero-configuration, and arbitrary self-hosted customer URLs cannot share the one exact callback without a common hosted callback/domain strategy. Atlassian requires one distributable integration for a customer-facing product. [3LO flow](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/). |
| GitHub OAuth App web flow | Registered OAuth App, callback URL, client ID and client secret; PKCE and `state` are recommended | Same-VPS callback works, but OAuth App repository access uses broad `repo`/`public_repo` scopes rather than one-repository permissions, so it is a poor fit. [web flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#web-application-flow), [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps). |
| GitHub device flow | A GitHub OAuth App or GitHub App must already be registered and device flow enabled; only client ID is needed during device exchange, not a client secret or redirect URI | It removes callback infrastructure and DSH can display the URL/code through its authorization notice vocabulary, but it does not remove app registration. OAuth App tokens remain broadly scoped; GitHub also advises limiting device flow to constrained/headless environments. [device flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow), [GitHub App security guidance](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app#dont-enable-device-flow-without-reason). |
| GitHub App installation | Registered App ID plus private key and an installation on the selected repository; installation tokens expire after one hour | Best production automation identity: repo-specific, permission-specific, app-attributed and user-independent. Deployment inference: the manifest flow can turn a Settings button into guided app creation and return the App ID/private key to a callback on this same VPS, followed by repository installation; no separately hosted callback service is required, but a reachable callback route and two GitHub confirmations remain. [manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest), [installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation). |

## DSH implementation consequences

Fixed Jira/GitHub tokens fit credential references and the existing browser credential Remote. OAuth and GitHub App credentials should instead be owner-scoped `GrantRecord`s: DSH keeps their JSON payload opaque, and `modifyRecord` is a serialized read-modify-write suitable for rotating tokens. Provider plugins should register `ctx.authorization` flows; that seam supplies URL/code notices, secret/text/select prompts, cancellation, one attempt per credential, and verifies that a fresh record was committed before reporting success. [record model and atomic update](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/credentials/credentials/src/index.ts#L154-L256), [authorization flow](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/credentials/authorization/src/index.ts#L120-L217), [attempt semantics](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/credentials/authorization/src/index.ts#L258-L312).

At this HEAD, authorization is a same-process service and no generic Remote/UI controller projects `list`, `begin`, prompts, or grant records to Web; the shipped credential Remote covers only fixed reference `describe/set/unset`. Autopilot therefore needs a small typed Host Remote for connection status/start/cancel and its own Settings contribution, while leaving token storage and attempt lifecycle to DSH. A browser callback cannot ride the authenticated `/api` carrier because cross-site requests are refused and the DSH session cookie is `SameSite=Strict`; register a narrow exact Host route through `ctx.webServer.register`, validate an unguessable single-use `state`, bind it to the pending attempt and expected provider, expire it promptly, and return no credential material to the browser. The Web server itself provides neither TLS nor route-wide authentication, so TLS remains the reverse proxy's responsibility and the callback route owns its security checks. [authorization interaction contract](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/credentials/authorization/src/index.ts#L139-L170), [exact route API](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/host/webserver/src/index.ts#L159-L172), [Web server security limit](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/host/webserver/README.md#known-limitations-and-deferred-work).
